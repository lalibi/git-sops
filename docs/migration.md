# Migrating encrypted repositories

## Moving the current checkout from git-crypt

Start with a clean, unlocked checkout. Keep the old git-crypt key for earlier commits. The migration reads the current working files and checks for files still in git-crypt format before writing the SOPS policy.

### Automated migration

Run from a clean, unlocked checkout. The command includes every tracked file with an effective `git-crypt` or named `git-crypt-*` filter.

```text
git-sops migrate-git-crypt --commit
```

By default the managed policy also covers `secrets/`. Use `--protect` to select additional files or directories in place of that default. A directory rule covers future files too. Files discovered through git-crypt that fall outside these directories get individual entries in `.sops.yaml`.

The migration reuses equivalent wildcard and directory rules in `.gitattributes`. To compact a file generated by v0.3.2, run `git-sops init` in the migrated checkout using the updated binary. It reads the existing path and recipient policy from `.sops.yaml`.

```text
git-sops migrate-git-crypt --protect secrets/ --protect appsettings.json
```

Optional removal of tracked `.git-crypt` recipient metadata:

```text
git-sops migrate-git-crypt \
    --protect secrets/ \
    --protect appsettings.json \
    --remove-git-crypt-metadata
```

### Removing git-crypt remnants

After the migration commit has been verified and backed up:

- remove tracked `.git-crypt/` metadata if it is no longer needed;
- inspect local git-crypt filter configuration:

```powershell
git config --local --get-regexp '^filter\.git-crypt'
git config --local --get-regexp '^diff\.git-crypt'
```

You may remove those local sections once you no longer need git-crypt for the current checkout.

Do not delete your old git-crypt key if historical commits may still need to be decrypted.

## Encrypting existing history in place

`protect` and `init` do not modify earlier commits. Use the separate history command on a clean, initialized repository:

```powershell
git-sops encrypt-history
# Include former paths and deleted paths explicitly:
git-sops encrypt-history --protect "old-secrets/,previous-name.json"
```

The command displays warnings and asks you to type **`rewrite history`** before preparing the rewrite. Noninteractive invocations fail unless explicit approval is supplied with `--confirm-rewrite`. That flag acknowledges the same warnings; do not add it casually to automation.

The rewrite:

- encrypts each selected historical version across all local refs, including branches, tags, remote-tracking refs and standalone root-tree checkpoints; additional paths extend the current managed set;
- preserves commit ancestry, merges, authors, committers, dates and messages, and preserves annotated tag metadata, while removing signatures tied to the old objects;
- adds the current managed SOPS policy and protection attributes to historical commits, preserving unmanaged attributes and updating existing nested attribute files;
- re-encrypts selected existing SOPS ciphertext for the current recipients, requiring a key that can decrypt historical versions;
- checks decryption of generated ciphertext, checks binary round trips, validates effective protection attributes and protected blobs in every rewritten commit, and checks Git object integrity before updating source refs;
- prepares objects in a temporary mirror and changes source refs in one transaction, then updates the current index and configuration while keeping local application files plaintext;
- retains a recovery bundle under the Git directory and prints its path; it does not push or prune old objects.

Historical rename detection is not automatic: list all former paths that need protection, and use a trailing `/` for deleted directories. SOPS may normalize formatting in structured formats, as in normal filter operation. Symlinks or submodule entries selected for encryption are rejected, and submodule repositories must be handled separately. Configuration files must stay plaintext; a protected directory containing its own `.gitattributes` is rejected. Repositories must be complete (not shallow), have no linked worktrees, replace refs or legacy grafts, and have committed `.gitattributes` and `.sops.yaml`. Standalone trees, including annotated tags pointing to trees, are interpreted as repository-root snapshots and encrypted and validated with the same policy as commits. Refs resolving to standalone blobs are rejected before preparing commits: a blob alone has no filename for matching protection rules. Checkpoint refs are rewritten rather than skipped, and their original targets are retained in the recovery bundle.

**Publishing is a separate, coordinated operation.** Review branches and tags, test a fresh clone with `git-sops join`, and arrange force pushes and fresh clones with collaborators. Remotes, forks and hosting caches are unchanged. The recovery bundle, reflogs and unreachable local objects retain the original history, possibly including plaintext. Keep the bundle securely and decide separately how to remove obsolete copies after validation. Rotate any credentials previously exposed in plaintext.

Remote-tracking refs are rewritten too, so plain `git push --force-with-lease` can fail with **`stale info`**: the local tracking ID is now a rewritten commit, while the server still has an original commit. After a successful rewrite, the command prints a push command for the current branch's configured upstream using its **original remote tip** as an explicit lease. Review that command before running it. It will refuse the push if the server's branch has advanced from the original tip.

For a previously completed rewrite, recover the original tracking tip from the printed recovery bundle. For example, from the affected repository in PowerShell:

```powershell
$bundle = '.git/git-sops-before-history-<printed-timestamp>.bundle'
$trackingRef = 'refs/remotes/origin/master'
$entry = @(git bundle list-heads $bundle $trackingRef)
if ($LASTEXITCODE -ne 0 -or $entry.Count -ne 1) { throw 'Could not recover the original remote tip.' }
$expected = ($entry[0] -split '\s+')[0]
git push "--force-with-lease=refs/heads/master:$expected" origin refs/heads/master:refs/heads/master
```

Use the correct remote and branch names for each branch you publish. This protects against server-side updates since the original tracking snapshot; it does not check whether the local branch incorporated every commit already known at that time. If the explicit lease is rejected, inspect the remote changes before deciding how to proceed. Fetching and then blindly retrying plain `--force-with-lease` replaces the original expectation with the latest remote tip and can overwrite changes you have not included. An ordinary `--force` push also discards the lease protection.

For recovery, inspect `git bundle list-heads <printed-bundle-path>` or clone the bundle into a separate directory. Keep the original bundle until the rewritten history has been independently verified.
